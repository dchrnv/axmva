## Passport

- **D1 ДНК как ключ** `[hypothesis]`. Вопрос: нужна ли отдельная сущность «правила чтения данных». Откуда: твой вопрос про «внутренние ключи»; в старых заметках ДНК токена это ключ чтения (порядок осей по уровням) `[analogy]`. Нужно ли: возможно нет. Как читать данные элемента уже говорят `inputs`/`outputs` с типами. Иначе: интерпретация живёт в схеме данных элемента, отдельного ключа нет. Вернуться, если появятся данные, которые один и тот же элемент читает по-разному.
- **D2 Формат `id` из пути** `[hypothesis]`. Разделитель и глубина. Нужно ли: да, но это техническое правило, не идея. Иначе: путь как есть, без правил.
- **D3 Автозапись в память** `[hypothesis]`. Единица записи, пороги `min_score`, `rate_limit` по источнику. Откуда: риск отравления памяти из первой спецификации. Нужно ли: только если память пополняется автоматически. Иначе: запись только по явной команде, тогда пороги не нужны, а `gate` остаётся с `accepts` и `provenance_required`.
- **D4 Третья ступень контракта** `[hypothesis]`. Нужна ли помимо `requires` / `bonus`. Нужно ли: скорее нет. Иначе: оставить как есть, вернуться по факту реальных контрактов.
- **D5 Язык значений `for_model`** `[hypothesis]`. Русский или английский. Нужно ли: только когда `for_model` реально используется. Проверка: один набор сценариев вызова на целевой слабой модели, сравнить долю ошибок.
- **D6 Схема самого passport** `[hypothesis]`. I11 требует файл схемы, он не написан. Нужно ли: возможно нет сейчас. Иначе: ручной чеклист из гайда, пока passport-файлов мало.
- **D7 Запускатель проверок** `[hypothesis]`. Правило «агенты не пишут `checks.yaml`, прогон запускает пользователь» принято (I27). Остаётся: нужен ли отдельный модуль-запускатель. Нужно ли: возможно нет. Иначе: один скрипт, который запускаешь ты.
- **D8 Два пути изменения** `[analogy]`. Правка поля и правка инварианта: один механизм или два (второй с кворумом или карантином). Откуда: выжимка старого документа KEY V 2.0. Нужно ли: скорее нет, пока агенты не меняют passport (I18). Иначе: один путь, утверждает пользователь.
- **D9 Мастер-ключ: что защищается и от кого** `[analogy]`. Заметка про автономность с мастер-ключом: защита от посторонних, но у владельца ключи от всех дверей. Сама заметка называет это непроработанным даже на уровне намерения. В passport уже есть `change_policy.approver: user` и I18. Нужно ли что-то ещё: не ясно. Противоречия с исходной идеей «шифровать», которые надо решить до переноса: неэкспортируемые ключи, потеря ключа как «смерть» системы, проверка только по поведению, отсутствие доступа для отладки. Файла `KEY V 2.0` в vault нет.
- **D10 Рассинхронизация версий** `[analogy]`. Элементы могут работать на разных версиях после обновления. Нужно ли: скорее нет, пока всё в одном дереве на одном ноутбуке. Иначе: сборка проверяется целиком по `assembly_hash`.
- **D11 Хеш** `[hypothesis]`. Алгоритм не выбран; входит ли `cost`. Нужно ли: хеширование было принципом первой спецификации, но для привязки результатов проверок хватает хеша одного passport. Иначе: без цепочки по зависимостям.
- **D12 Гайды для элементов** `[hypothesis]`. Откуда: твоя просьба про гайды «позже, для новой сущности». Нужно ли: да. Вернуться, когда появится первый элемент с кодом.
- **D13 Общие параметры сборки** `[analogy]`. Четвёртый раздел старого конституционного слоя. Нужно ли: скорее нет. Иначе: параметры лежат в passport элементов.
- **D14 Пороги по регионам (октанты)** `[fantasy]`. Октанты как набор мембран с отдельным порогом каждая. Нужно ли: нет, пока `gate` по источникам не окажется грубым. Иначе: пороги по источникам.
- **D15 Роли доступа и уровень «вето»** `[analogy]`. Откуда: заметка про Zero-trust (три уровня: наблюдатель, оператор, контроллер). Нужно ли: только когда появится элемент с такой ролью. Что уже выражается без новых полей `[hypothesis]`:
  - роль по функции выводится из связей, как `state`, и не хранится: наблюдатель это только `read`-связи, оператор пишет не более чем в 1-2 места (предел проверяется сканом сборки), контроллер это вето;
  - обязательный арбитраж внешнего эффекта это топология: passport-прокси `external` принимает запись только от одного элемента-арбитра, проверка сканом;
  - «невыразимо по построению» уже в гайде как `invariant` с тестом.

  Что не переносится: в заметке контроллер может инициировать изменения правил, у нас по I18 и I28 это максимум рекомендация. От третьего уровня остаётся вето. Варианты оформления вето: `mode: veto` в связи или обычный элемент с `invariant` «не пропускает X». Новый `kind` не нужен (I22). Сквозной сценарий из заметки (восприятие, симулятор, арбитр, исполнитель, наблюдатель) годится как приёмочный `invariant` passport сборки, когда сборка перестанет быть пустой.
- **D16 Журнал и воспроизведение** `[analogy]`. Из Zero-trust: наблюдатель пишет только изменения, чтобы после сбоя «отмотать время». Нужно ли: не очевидно. Это поведение кода; вопрос только в том, нужно ли обязательство «ведёт журнал записей с источником» в `guarantees`. Иначе: журнал как деталь реализации элемента, не как поле passport.
