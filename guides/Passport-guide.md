# Гайд: как написать passport для нового элемента

Процедура. Описание полей и таблиц здесь не повторяется: см. [[Passport]]. Правила и имена: [[Invariants]]. Нерешённые вопросы: [[Deferred]].

Passport пишется сразу, как появилась идея элемента, а не после кода. Элемент проходит лестницу `stub → training → connected`, и на каждой ступени заполняется ровно то, что уже известно.

## Шаг 0. Выбрать путь и kind

Путь определяет `id` (N2): положи папку элемента на нужное место и не придумывай имя отдельно. Затем ответь на вопросы по порядку, первое «да» даёт `kind`:

1. Это корень сборки? → `assembly`.
2. Элемент не в нашем дереве, мы им не владеем? → `external`.
3. Это неизменяемые данные (пак, словарь, константы), только чтение? → `data`.
4. Это модель, которая недетерминирована и считается по бюджету ноутбука? → `model`.
5. Иначе → `code`.

Если ничего не подходит, смотри I22: новый `kind` нужен, только если у него есть правило по умолчанию, которого нет в таблице.

## Шаг 1. Стаб

Заполни `kind`, `status`, `version`, `role`. Больше ничего не требуется.

- `status`: `hypothesis`, если это план; `analogy`, если взято из прошлого проекта; `fantasy`, если это исследование без обязательств; `done` только когда есть код и проверка (шаг 5).
- `role`: одна фраза. Если фраза не помещается, элементов два.

Состояние: `stub`.

## Шаг 2. Интерфейс

Заполни `inputs`, `outputs`, `depends_on`, `must_not_touch`, `links_in`.

- Для каждого входа задай источник и режим. Всё, чего нет в `links_in`, запрещено.
- Если принимаешь данные из памяти, от агента или извне, добавь `gate`: `accepts`, `rate_limit`, `min_score`, `provenance_required`. Пороги числовые.
- Источник в `gate` это идентичность связи (`from`), а не поле в самом сообщении: заявлению отправителя о себе не верим.
- Если связь двусторонняя, это две записи, каждую пишет принимающий элемент.

## Шаг 3. Контракт

Для каждого обещания заведи пункт в `requires`.

- **`invariant` или `target`.** Вопрос: если это нарушено, элемент нельзя подключать? Да → `invariant`. Нет, достигается со временем → `target`.
- У каждого пункта `test`, `metric`, `threshold`. Порог записывается до первого прогона (I14).
- Статус пункта (`status`) отдельный от статуса элемента: пункт может быть `hypothesis`, пока элемент `done`.
- Что приятно, но не обещано, идёт в `bonus`. Известные потери идут в `known_losses`, это не скрытые баги.
- Значения измерений в passport не пишутся. Они только в `checks.yaml`.
- **Границы доступа и безопасность это тоже `invariant` с тестом.** Пример: попытка записи в чужую полку возвращает отказ. `must_not_touch` без теста остаётся заявлением, а не гарантией.

## Шаг 4. Часть для модели

Заполни `for_model`, только если элемент зовёт модель.

- Утверждения «да или нет», коротко, без «возможно».
- Всё, что модель должна делать и не делать, идёт в `rules.always` и `rules.never`.
- Описание инструментов в формате MCP, плюс `errors` (что делать при ошибке) и `examples`.
- Эти поля пишешь ты. Внешний текст сюда не вставляется.
- Агент видит только проекцию passport по белому списку полей (I7). Если хочешь, чтобы новое поле видел агент, добавь его в белый список явно.

## Шаг 5. Проверка и подъём статуса

1. Запусти тесты из контракта, запиши результаты в `checks.yaml` с текущим `element_hash`. Прогон запускаешь ты, агент `checks.yaml` не пишет (I27).
2. Измени `status` на `done` только когда у каждого `invariant` есть действующий `passed`. Иначе состояние станет `inhibited` (честность статуса).
3. Если `target` не достигнут, элемент остаётся `training`: он подключается, но помечен.

## Шаг 6. Версия и журнал

- Обещание не менялось → patch. Что-то добавилось → minor. Убрано или изменился смысл → major, и сборка проверяет `compat`.
- Любое решение, которое не очевидно из самого файла, одной строкой в журнал решений в [[Passport]] с версией и причиной.
- Старые копии не храни: новая версия включает прежнюю.
- Запись в `Deferred`, журнале или `open_questions`, сделанная агентом, не даёт ему права на правки: решение всегда от тебя (I28).

## Типичные ошибки

- В контракт записано число измерения (должно быть в `checks.yaml`).
- `status: done` без результата проверки.
- `invariant` без теста или без порога.
- Порог подогнан после прогона.
- В `for_model` стоят «возможно», «обычно», «как правило».
- Свободный текст в `note` вместо поля контракта.
- Связь не объявлена в `links_in`, а данные текут «по умолчанию».
- Граница доступа заявлена в `must_not_touch`, а теста нет.
- Источник в `gate` берётся из содержимого сообщения.
- Обещание изменилось, `version` нет.

## Проверка перед тем, как считать passport готовым

- Путь и `kind` выбраны по шагу 0.
- Для `done`: `inputs` и `outputs` есть.
- Каждый `invariant`: `test`, `metric`, `threshold`.
- Каждый принимаемый вход: запись в `links_in`; для внешних и памяти есть `gate`.
- В хешируемых полях нет значений измерений и внешнего текста.
- Запись в журнале решений для каждого неочевидного решения.
