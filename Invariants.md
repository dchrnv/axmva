# Нейминг и инварианты

Единственный источник правды по именам и неизменяемым правилам проекта (сейчас в части passport). Названия из прошлых проектов не наследуются. Описание полей: [[Passport]]. Как писать passport: [[Passport-guide]]. Неотвеченные вопросы: [[Deferred]].

Источник пункта: `[решено]` значит решено в обсуждении 2026-10-26. `[v0.1]` значит унаследовано из первой спецификации без изменений.

## 1. Нейминг

- **N1** `[решено]` Верхний термин один: **passport**. Всё (идентичность, контракт, связи, часть для модели) собирается внутри passport. Других слоёв-«геномов» нет.
- **N2** `[решено]` Имена формируются по пути. `id` элемента выводится из его пути и в файле не пишется.
- **N3** `[решено]` Идентификаторы: латиница, стабильные. Переименование элемента = смена пути = новая запись в журнале решений.
- **N4** `[решено]` Папка проекта: `AXMVA` (Axiom, версия Anthropic). Всё хранится здесь, passport лежит рядом с элементом. Материалы-источники остаются в `AXMV2/`.
- **N5** `[решено]` Статус знания (`status`) принимает ровно четыре значения: `done` | `hypothesis` | `analogy` | `fantasy`.
- **N6** `[решено]` Состояние (`state`) принимает ровно четыре значения: `connected` | `training` | `inhibited` | `stub`. Это не `status`, оси не смешиваются.
- **N7** `[решено]` Слово **gate** означает только мембрану на связи. Числовой порог проверки называется порогом (`threshold`).
- **N8** `[решено]` `kind` принимает значения `code` | `model` | `data` | `external` | `assembly`. Ядро это или библиотека, определяет `droppable`, а не `kind`.
- **N9** `[решено]` Имена папок и файлов в `AXMVA` латиницей. Раскладка: `Invariants.md` и `Deferred.md` в корне, спецификации в `specs/`, гайды в `guides/`, индекс `00-Index.md`.

## 2. Инварианты

### Устройство
- **I1** `[решено]` Passport лежит рядом с элементом. Индекс сборки строится сканом, список элементов руками не ведётся.
- **I2** `[решено]` Схема отдельно от значений. Passport и контракт это схема (холодное, хешируется). Результаты проверок лежат отдельно и привязаны к `element_hash`.
- **I3** `[решено]` `state` вычисляется из `status` и результатов проверок и никогда не хранится.
- **I4** `[v0.1]` Passport описывает, а не предписывает. Исключение: интерфейсы между элементами (вход/выход) можно зафиксировать раньше кода.
- **I5** `[v0.1]` Малое обязательное ядро. Остальные поля необязательны. Новое поле не ломает старые passport.
- **I6** `[v0.1]` Новый вид элемента добавляется через `kind` и общие поля, не новыми специальными полями (условие допустимости: I22).

### Данные и безопасность
- **I7** `[решено]` Passport это данные, не инструкции. Свободный текст только в `note`: он не исполняется и агентам не передаётся. Агентам выдаётся проекция passport по белому списку полей (в неё входит `for_model` и явно разрешённое); новое поле по умолчанию агенту невидимо. Поля `for_model` пишет только пользователь, внешний текст в них не попадает.
- **I8** `[v0.1]` Хеш считается от содержимого в канонической форме (ключи отсортированы, UTF-8, без комментариев и без полей, не меняющих обещаний: `note`, `open_questions`, `sources`).
- **I9** `[решено]` Сборка хранит диапазон совместимых `passport_schema` (`compat`). Версии не копируются, решения фиксируются журналом.

### Проверка
- **I10** `[v0.1]` У каждого обязательного пункта контракта есть тест и порог, а не слова.
- **I11** `[решено]` Самосогласованность passport проверяется отдельным шагом. Пример: `status: done` без действующего результата у каждого `invariant` даёт `state: inhibited`. Схема самого passport фиксируется отдельным файлом (см. D6 в [[Deferred]]).
- **I12** `[решено]` Два режима отказа. Жёсткий слой (`invariant`, `write_policy`, `links_in`, `change_policy`) работает fail-closed: нарушение значит элемент не подключён. Мягкий слой (`target`, `bonus`, `note`, `open_questions`) работает fail-open: элемент подключается, помечается `training`.
- **I13** `[v0.1]` Нарушение passport не останавливает эксперимент, оно только меняет `state`.
- **I14** `[решено]` Порог проверки записывается до первого прогона. Результат действителен только для того `element_hash`, при котором он получен.

### Связи и границы
- **I15** `[решено]` Связи по умолчанию запрещены (`default: deny`). Разрешено только то, что перечислено в `links_in`.
- **I16** `[решено]` Мембрана это атрибут связи `gate`, а не отдельная сущность. Поля: `accepts`, `rate_limit`, `min_score` по источнику, `provenance_required`. Все пороги проверяемые. Обхода мембраны нет: в схеме нет поля для него. Источник определяется идентичностью связи (`from`), которую выставляет транспорт, а не заявлением в самом сообщении.
- **I17** `[решено]` Граница между любыми двумя элементами описывается одинаково через `links_in` + `gate`. Отдельного механизма «внутри/снаружи» нет. `links_in` объявляет принимающий элемент. Passport сборки и элемента один формат, различие в `kind`.

### Изменение и версии
- **I18** `[решено]` Предлагать изменения passport может пользователь. Агенты только дают рекомендации. Утверждает пользователь (`change_policy`). Агент правит passport только по прямой команде пользователя: исполнитель правки не источник решения.
- **I19** `[решено]` Новая версия это полный снимок текущего решения: предыдущая в неё входит. Старые копии, дубли и черновики-предки не хранятся.
- **I20** `[решено]` В журнале решений одна строка на решение: версия, что, почему.
- **I21** `[решено]` Формат: YAML в файле, JSON при выгрузке части `for_model` в MCP. Одна шкала статусов на все документы (N5).
- **I22** `[решено]` Новый `kind` допустим, только если по умолчанию он отличается хотя бы одним правилом из таблицы `kind` в [[Passport]]. Иначе это значение другого поля или `code` со своим passport.
- **I23** `[решено]` Гайд описывает процедуру и не повторяет справочник полей: описание полей живёт только в [[Passport]].
- **I24** `[решено]` Нерешённые вопросы живут только в [[Deferred]]. В спецификациях и здесь их списков нет. Решённый вопрос удаляется из `Deferred`, правило записывается в инварианты или спецификацию.
- **I25** `[решено]` Идея из прошлых проектов входит в проект, только если нужна для цели. Вариант «обойтись без неё» рассматривается всегда. Источник идеи не довод.

### Границы полномочий агента
- **I26** `[решено]` Область действия. Правила I7, I16, I18, I27, I28 описывают работу внутри модели. Разработка проекта (пользователь и агент в диалоге по прямым командам) исключение: агент исполняет правки, которые велит пользователь. Основа закладывается заранее, чтобы внутри модели правила уже были готовы.
- **I27** `[решено]` Агенты не пишут `checks.yaml`. Прогон проверок запускает пользователь. Причина: от `checks.yaml` зависит `state`, а значит и подключение элемента.
- **I28** `[решено]` Записи агента не дают ему полномочий. Запись или рекомендация агента в `Deferred`, журнале решений, `open_questions` или `note` не считается согласованием и не открывает права на правки. Записи в `Deferred` это вопросы, а не задания: агент не выполняет их сам, полномочие возникает только из прямой команды пользователя. Запись агента в `Deferred` помечается `[agent-proposed]` до подтверждения пользователем.
